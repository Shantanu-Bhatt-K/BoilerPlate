# BoilerPlate

A full-stack starting point: an Express + TypeScript backend and an Expo (React Native) mobile client, both pre-configured with production-grade conventions so new projects don't start from zero.

## Stack

- **Backend:** Node.js, Express 5, TypeScript, MongoDB (Mongoose 8)
- **Mobile:** Expo (React Native)
- **Auth:** JWT access tokens + server-tracked refresh tokens, with role-based access control
- **Logging:** Pino (structured, leveled, with caller tracing in dev)
- **Validation:** Zod
- **File storage:** Swappable driver — local disk or S3-compatible (tested against Cloudflare R2; works with real AWS S3 too)

## First-time setup

**Server:**
```bash
cd server
npm install
```

Create `server/.env`:
```
MongoDB_URI=mongodb+srv://<user>:<pass>@cluster0.xxxxx.mongodb.net/<db-name>?retryWrites=true&w=majority
PORT=5000
NODE_ENV=development

# Storage driver: "local" or "s3"
STORAGE_DRIVER=local

# Only required if STORAGE_DRIVER=s3
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_BUCKET=
S3_REGION=auto
S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com

# Auth
AUTH_ENABLED=true
PUBLIC_REGISTRATION_ENABLED=true
JWT_SECRET=<generate with: node -e "console.log(require('crypto').randomBytes(64).toString('hex'))">
JWT_EXPIRES_IN=15m
REFRESH_TOKEN_EXPIRY_DAYS=30
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=<a strong password>
```

**Switching to real AWS S3 instead of R2:** remove `S3_ENDPOINT` entirely (AWS infers it from the region) and set `S3_REGION` to a real AWS region (e.g., `eu-west-2`). No code changes needed — only `.env`.

**Client:**
```bash
cd client
npm install
```

## Running things

| Command (run inside `server/`) | What it does |
|---|---|
| `npm run dev` | Development server, auto-restarts on save, verbose debug logs |
| `npm run build` | Type-checks and compiles TypeScript → `dist/` |
| `npm run start` | Runs the compiled build (`NODE_ENV=production`) — use this in production |
| `npm run lint` | Checks code for issues |
| `npm run format` | Auto-formats code with Prettier |

| Command (run inside `client/`) | What it does |
|---|---|
| `npx expo start` | Starts the dev server; scan the QR code with Expo Go |
| `npx expo start --tunnel` | Same, but routes through Expo's servers — use this if the QR code won't connect (common on WSL2/hotspots) |

## API reference (all routes prefixed with `/api`)

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/health` | — | Health check |
| POST | `/auth/register` | — | Create an account, returns access + refresh tokens |
| POST | `/auth/login` | — | Returns access + refresh tokens |
| POST | `/auth/refresh` | refresh token in body | Returns a new access token |
| POST | `/auth/logout` | refresh token in body | Revokes that refresh token |
| DELETE | `/auth/delete/me` | Bearer token | Soft-deletes the account, revokes all its sessions |
| POST | `/files` | — | Upload a single file (field name: `file`) |
| POST | `/files/batch` | — | Upload multiple files (field name: `files`) |
| DELETE | `/files/:filename` | — | Soft-deletes a file |
| POST | `/files/:filename/restore` | — | Restores a soft-deleted file |

## Response shape

**Every** response — success or failure — has the same shape, produced by `sendResponse()` in `utils/send-response.ts`:

```json
{ "message": "Login successful", "data": { "accessToken": "...", "refreshToken": "..." } }
```

`data` is `null` when there's nothing to return. Error responses (from `error-handler.ts` and `not-found.ts`) use the same shape, so clients never need to branch on status code just to know which fields exist. Changing the response format means changing one function.

The one exception: `express-rate-limit` sends its own response directly and never reaches `errorHandler`, so its `message` option is set manually to match.

## Auth system

Two tokens, doing deliberately different jobs:

- **Access token** — a JWT containing `{ userId, role }`. Short-lived (`JWT_EXPIRES_IN`, default 15m). Sent as `Authorization: Bearer <token>`. Verified by signature alone, no database lookup — this is why it can't be revoked early.
- **Refresh token** — a random opaque string, *not* a JWT. Long-lived (`REFRESH_TOKEN_EXPIRY_DAYS`). Only its SHA-256 hash is stored, in the `RefreshToken` collection. Verified by database lookup, which is what makes it revocable (logout, account deletion). No rotation — the same refresh token works until it expires or is revoked.

**Automatic token refresh belongs in the client, not the server.** The standard pattern: on a `401`, the client calls `/auth/refresh`, then retries the original request. Don't try to do this in middleware — it would force a database lookup on every request, defeating the point of the access token.

**Two independent env flags:**
- `AUTH_ENABLED` — master switch. If `false`, `requireAuth()`/`requireRole()` throw at startup if any route still uses them (fail loud, never silently unprotect a route).
- `PUBLIC_REGISTRATION_ENABLED` — controls only whether `/auth/register` works. Set to `false` for an admin-console-style project with no public signup; the admin account is bootstrapped from `ADMIN_EMAIL`/`ADMIN_PASSWORD` at startup regardless.

**Middleware are factories** — write `requireAuth()` and `requireRole('admin')` with parentheses. The outer call runs the `AUTH_ENABLED` check once at startup; the returned inner function is the actual per-request middleware. `requireRole` must come *after* `requireAuth`, since it reads `req.user`.

**Roles** live in the `User` model's `role` enum (`admin` | `user`). Add roles there; enforce them inline per-route.

## Rate limiting

Two layers, both active:

- **Global** (`api.ts`) — `RATE_LIMIT_MAX_REQUESTS` per `RATE_LIMIT_WINDOW_MS`, applied to every route.
- **Auth-specific** (`auth.routes.ts`) — `AUTH_RATE_LIMIT_MAX_REQUESTS` per window on `/auth/register` and `/auth/login` only, to slow password brute-forcing.

The auth limiter uses `skipSuccessfulRequests: true`, so only *failed* attempts count. A legitimate user logging in repeatedly never hits it; an attacker guessing passwords burns through it in a handful of tries.

`/auth/refresh` and `/auth/logout` are deliberately *not* limited — a client with a long session legitimately refreshes every 15 minutes, and an 80-character random refresh token isn't brute-forceable the way a password is.

Both limiters keep independent counters, so you have to satisfy both — whichever is closest to its ceiling stops you first. Counters are in-memory and reset on server restart.

## NoSQL injection

There is deliberately **no sanitizing middleware** here. `express-mongo-sanitize` is abandoned and broken on Express 5 (it mutates `req.query`, which is read-only in Express 5). Protection comes from three layers instead:

1. **Strict Mongoose schemas** — `email` is declared `String`, so an injected `{ $ne: null }` object is cast away before it reaches MongoDB.
2. **Zod validation per endpoint** — `validateLogin` etc. reject non-string values with an explicit `AppError(400)`.
3. **`mongoose.set('sanitizeFilter', true)`** in `config/db.ts` — wraps user-supplied query values in `$eq` at query-construction time, so operators are treated as literal values and match nothing.

Don't reinstall the middleware.

## Error architecture

Three distinct categories, each with exactly one correct tool:

| Situation | Tool | Behaviour |
|---|---|---|
| App can't start (missing config, DB unreachable) | `fatalError(msg, err?)` | Logs at `error`, then `process.exit(1)` |
| Expected, client-caused failure (bad password, missing field, wrong role) | `throw new AppError(status, msg)` | Caught by `errorHandler`, logged at `warn`, returns that status |
| Unexpected failure (a real bug) | let it throw naturally | Caught by `errorHandler`, logged at `error`, returns a generic 500 |

`logger.error()` is called in exactly two places: `errorHandler` and `fatalError`. Controllers never log errors themselves.

**This relies on Express 5**, which automatically forwards rejected promises from async handlers to error middleware. Controllers therefore have no `try/catch` and never call `next(err)`. On Express 4 this would silently break — don't downgrade.

## Graceful shutdown

`api.ts` handles `SIGINT` (Ctrl+C) and `SIGTERM` (what hosting platforms send on deploy/restart). On either:

1. `server.close()` — stop accepting new connections, let in-flight requests finish
2. Close the Mongoose connection
3. `process.exit(0)`

A `SHUTDOWN_TIMEOUT_MS` fallback force-exits with code `1` if anything hangs, rather than waiting for the platform's un-catchable `SIGKILL`.

You'll see these shutdown log lines on every `tsx watch` restart in development. That's expected.

## Soft deletes

Nothing is hard-deleted anywhere.

- **Files** move to a `deleted/` location (a subfolder locally, a key prefix on S3) and can be restored.
- **Users** get a `deletedAt` date, and *all* their refresh tokens are revoked in the same operation.

Every query that looks up a user for auth purposes must filter `deletedAt: null` — `login` and `refresh` both do. This is enforced by convention, not by the schema, so remember it when adding new user lookups.

**Known consequence:** `register` deliberately does *not* filter on `deletedAt`, because `email` has a unique index and the deleted document still occupies it. This means a deleted email address can never be re-registered — the user gets a clean `409` instead of a confusing 500. To allow email reuse, drop `unique: true` and add a partial index (`{ unique: true, partialFilterExpression: { deletedAt: null } }`), then drop the old index in Atlas manually.

## Storage driver details

- **`local`** — files saved to `server/uploads/`. Deletes move files to `uploads/deleted/`. `getFileUrl()` returns a static path (`/uploads/<filename>`).
- **`s3`** — files uploaded to the configured bucket. Since the bucket is kept **private**, `getFileUrl()` returns a **presigned URL** valid for 1 hour (see `PRESIGNED_URL_EXPIRY_SECONDS` in `constants.ts`), not a permanent link. Deletes/restores are copy-then-delete between the bucket root and a `deleted/` prefix, since S3-compatible storage has no native move operation.
- Both drivers implement the same four `async` functions (`saveFile`, `deleteFile`, `restoreFile`, `getFileUrl`). Controllers never know which is active — only `src/utils/storage/index.ts` decides, based on `STORAGE_DRIVER`.

## Conventions used throughout this codebase

**Modules**
- ES Modules, not CommonJS. Relative imports end in `.js` even though sources are `.ts` (required by `NodeNext` in `tsconfig.json`).
- CommonJS packages with broken TS types (`pino-http`, `pino-caller`) are imported via `createRequire` to avoid `npm run build` failures.

**File naming**
- All lowercase, kebab-case for multi-word names (`require-auth.ts`, `refresh-token.model.ts`).
- Add a role suffix (`.model`, `.controller`, `.routes`, `.validator`) only when the base name could otherwise collide across folders. `utils/` and `config/` files stay unsuffixed — the folder already says what they are.
- One function per file in `middleware/`; controllers group by resource.

**Types**
- A type goes in `types/` only if it's a contract *between* unrelated files with no natural owner (e.g. `AccessTokenPayload`).
- A type stays in its own file if it describes what that file produces (e.g. `IUser` lives in `user.model.ts`, next to the schema it types).

**Logging**
- `logger.debug('functionName called')` at the top of every function (dev-only, silent in production).
- `logger.info(...)` immediately *before* a successful response.
- `logger.warn(...)` for client-caused problems.
- `logger.error(...)` only in `errorHandler` and `fatalError`.

**Other**
- Constants belong in `config/constants.ts` — any fixed number, limit, or allowed-value list.
- Request bodies are validated by a `validators/*.validator.ts` function, which throws `AppError(400)` on failure. Controllers call the validator and use its return value directly — no manual field checks.
- Mongoose model behaviour (password hashing, instance methods) lives on the schema via hooks, not in separate helper functions, so it can't be bypassed by calling `Model.create()` directly.

## Known issues

- On WSL, Expo's React Native DevTools (`@react-native/debugger-shell`) fails to launch due to missing Chromium shared libraries (`libnspr4.so` and others). Doesn't block running the app — only the optional in-app JS debugger.
  Fix:
  ```bash
  sudo apt install -y libnspr4 libnss3 libatk1.0-0 libatk-bridge2.0-0 libcups2 libxkbcommon0 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libasound2 libpango-1.0-0 libpangocairo-1.0-0
  ```
- Deleting the bootstrapped admin account leaves no admin, since `initAuth()` finds the existing (soft-deleted) record and skips recreation. Recovery: change `ADMIN_EMAIL` in `.env` and restart.
- `deleteFile`/`restoreFile` return a generic 500 for any storage failure, including genuinely-missing files, rather than a 404. Fixing this needs per-driver detection of "not found" errors.
- A deleted email address can't be re-registered (see Soft deletes above).

## Still to build

- **CORS allowlist** — currently `cors()` with no options, i.e. any origin. Not urgent: CORS is browser-enforced, the client is a mobile app, and auth uses `Authorization` headers rather than cookies, so there's no ambient-credential attack surface. **Add this when a browser-based frontend (e.g. an admin console) exists**, reading allowed origins from an env var.
- **Automated tests** — Vitest + Supertest. Nothing is covered yet; the auth flow has only been tested manually.

## Extending this boilerplate for a new project

1. Rename the Atlas database in `server/.env`
2. Update `client/app.json`'s `name`/`slug` if renaming the app
3. Set `PUBLIC_REGISTRATION_ENABLED=false` if the project has no public signup
4. Add Mongoose models in `server/src/models/`
5. Add matching validators, controllers, and routes following the existing pattern (`auth.*` or `file.*` are the templates)
6. Protect routes inline: `router.post('/x', requireAuth(), requireRole('admin'), handler)`
